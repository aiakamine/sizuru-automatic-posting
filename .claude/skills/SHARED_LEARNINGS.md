# スキル共通の学び

mitchaku / taidan のどちらにも当てはまる学びを置く。**改善フェーズ（各スキルの `DREAM.md`）で
「もう片方のスキルにも当てはまるか」を必ず確認し、当てはまるならここに書く。**
各スキルの `references/hearing.md` は、ヒアリングの前にこのファイルも読む。

書き方：`## 分類` の下に、`- 学び（日付・根拠）` の形で1行ずつ。古くなったら消す。

## 素材の取得

- **yt-dlp は版が古いと失敗する。** PATH 先頭の 2025.10.14 版はプラグインエラー
  （`debug() got an unexpected keyword argument 'once'`）と空ファイルで失敗し、Homebrew の
  2026.8.19 版（`/opt/homebrew/bin/yt-dlp`）で取得できた。取得前に `yt-dlp --version` を見る（2026-09-15）
- 403 は `--cookies-from-browser chrome` で回避。`player_client` 切替では360pしか取れない

## 書き出し

- **背景画像の入力は fps を明示する。** `-loop 1 -i base.png` は既定25fpsで、overlay の出力
  タイミングを支配してしまう。29.97fps の映像が25fps相当に間引かれ、重複フレームが
  90フレーム中15枚出ていた（2026-09-16、mitchaku で実測。taidan は lavfi の color 入力に
  `r=FPS` があるため同じ問題は起きない）
- **ラウドネスは2パスで内蔵する。** 1パスの loudnorm は素材によって -15〜-16 LUFS に外れる。
  書き出し後に ebur128 で実測し、-14±0.5 を外れたら measured_* 付きで音声だけ正規化し直す（2026-09-16）
- **カット点はフレーム格子にスナップする。** float 秒のまま trim に渡すと、実出力のフレーム数と
  検査側の想定時刻がずれ、境界で誤判定が出る（2026-09-16）
- **秒の丸めでカット端の1フレームが落ちることがある。** `-ss` を `.3f` で丸めて渡すと、実際の
  シーク位置が理論値からサブミリ秒（実測で0.07ms程度）ずれ、そのわずかな差で trim の境界
  フレームが窓の外に落ちる。trim の start・end を半フレーム前倒しする安全マージンを持たせて
  解決した（`-t` も同様に半フレーム延長する）。境界ちょうどを狙う計算は、丸め誤差1msにも満たない
  差で1フレーム丸ごと落ちうるので、半フレーム級の余裕を必ず持たせる（2026-09-17、mitchaku で実測）
- **音声ストリームがコンテナ全体の基準時刻より遅れて始まる素材がある（edit list等）。**
  全編を1回だけPCMに読み込んでインデックス＝絶対時刻として窓ごとに計算する設計
  （`chop.py`/`cutpoints.py`）は、そのままだと音声開始前の時刻を「音声あり」、
  終端付近を範囲外で「無音」と誤判定する。音声ストリームのstart_timeと
  フォーマット全体のstart_timeの差だけ無音でパディングして補正する
  （ストリーム単体の絶対start_timeをそのまま使うと、全ストリームが同じだけ
  後ろにずれている素材で実際には遅れが無いのに誤って大きなパディングを入れてしまう
  ので、差分を取ることが必須）。デコード側も同じストリームを`-map`で明示指定する
  （複数音声トラックがあると自動選択でズレる）。**既知の限界：ストリーム内部で
  タイムスタンプが不連続（パケット欠落等）な区間があるケースは未検証。**
  `aresample=async=1`で軽減を試みているが、ダウンロードしたYouTube動画・画面録画
  では通常発生しない前提。発生した場合は境界ごとに直接シークする方式（旧chop.pyの
  db()）にフォールバックする（taidan-kirinuki/common.py、2026-09-17、Codexレビューで検出）
- **`ffmpeg -ss` は要求した1フレームちょうどを返すとは限らない。** フレーム中央
  `(frame+0.5)/fps` でのシークが、実測（`tests/regression/fixture/clip.mp4`、input seek）
  では要求フレームの次のフレームを返すことがあった。1フレームの取り違えが許容できない
  用途（ピクセル単位の頭尻突合せ等）では、フレーム境界`frame/fps`での抽出や、複数フレームを
  抜いて期待値と突き合わせる設計にする。逆に「大まかに一致するかどうか」を二分探索で
  探すような用途（フェードイン検出の開始フレーム補正等）では1フレームのずれは実害が小さい
  （taidan-kirinuki/subtext.py、2026-09-17、Codexレビューで検出）
- **loudnorm の `print_format=json`（input_i）と ebur128 の Integrated loudness は
  同じ素材でも最大0.3LU程度食い違う（loudnormの方が低めに出る系統的バイアス）。** 判定・検証は
  ebur128 に統一する。loudnorm の測定値は「2回目パスに渡す measured_\* の実測」専用に限定し、
  合否判定には使わない（2026-09-17、mitchaku で実測）
- **ラウドネス補正を重ねるとTrue Peakがかえって悪化することがある。** 2回目の補正が
  実質0dB（True Peakのceilingに余裕が無くこれ以上ブーストできない）でも、音声だけ再エンコード
  し直すとAACの世代重ねでTrue Peakが増える（実測で-1.2dBFS→+0.4dBFSに悪化）。クランプ後の
  ゲインが微小（目安0.1dB未満）なら、その補正パスの再エンコードごとスキップする
  （2026-09-17、mitchaku で実測）

## 検査

- **OCR の読み揺れを合否に直結させない。** 「=」と「三」、「0」と「の」、2行テロップの行順が
  入れ替わるなど。警告が出たら実フレームの OCR で裁定する（2026-09-15）
- **テロップ本文＝発話とは限らない。** テロップが語を補うことがあり、テロップの切替で切ると
  音声が途中から始まる。頭の語は Whisper の単語時刻で確認する（自動字幕はタイミングが不正確）（2026-09-15）
- **自己ベースラインのハッシュ比較だけでは「最初から壊れた値」を記録してしまう。** フレーム欠落で
  空データのMD5（`d41d8cd98f00b204e9800998ecf8427e`）を期待値として保存してしまった実例がある。
  空データのMD5・出力フレーム数とtimelineのtotal_framesの不一致は必ずFAILにし、
  `--update-expected` でも壊れた値を記録させない。加えて、出力の頭尻フレームを元素材の対応
  フレームと画素レベルで突き合わせ（隣接フレームより近いことも確認）、頭尻ずれ自体を検出する
  （2026-09-17、mitchaku の回帰テストで実装）

## 並列実行

- **`xargs -P N -I{} sh -c '{}'` は作業フォルダのパスが長いと壊れる。** `-I{}` の置換後の
  コマンド長がOSの上限（macOSは255バイト目安）を超えると「command line cannot be assembled,
  too long」で落ちる。スクラッチパッド配下の長いパスで実際に再現した
  （taidan-kirinuki/subtext.py、2026-09-17）。シェル文字列を経由する並列実行はやめ、
  `concurrent.futures.ThreadPoolExecutor` で `subprocess.run` を直接呼ぶ（argvリストのまま
  渡すのでパス長の制限を受けない。失敗したジョブがあれば例外を伝播させ、黙って一部だけ
  欠けたまま進まないようにする）

## フックと運用

- SKILL.md の frontmatter に書いたフックは、スキル起動後そのセッション中だけ有効。
  フック内では `${CLAUDE_SKILL_DIR}` が空になるので、候補パスを順に探す（2026-09-15 実測）
- Stop フックの注意は「1回の終了につき1回」。続けて終えれば通るので、
  「必ず止まる」ではなく「毎回気づかせる」仕組みとして扱う（2026-09-16）
- 待ち時間（サブエージェントや長い書き出し）のたびに注意が出ると邪魔になる。
  出力の顔ぶれが変わったときだけ知らせる（2026-09-16）
