# DREAM — 改善フェーズ（taidan-kirinuki）

使うたびにスキルを賢くするための手順。**納品のたびに毎回**行う。
記録は `$D/improve.md`（雛形 `templates/improve.md`）。`$D/out/` に mp4 があるのに
`状態: 完了` になっていなければ、stop_improve フックが終了を差し戻す
（注意は mp4 の顔ぶれが前回から変わったときだけ。1回の終了につき1回で、続けて終えれば通る）。

**スキルのファイルを変えるのは、ユーザーが承認した提案だけ。** 承認なしに SKILL.md・references・スクリプトを書き換えない。

## 1. FB を聞く

各本について AskUserQuestion で聞き、`## 今回のFB` に書く。

- 評価：そのまま使える／手直しすれば使える／使えない
- 観点ごとの良し悪しと理由：シーン選定／フック／繋ぎと終わり方／バナー文言／投稿タイトル・ハッシュタグ
- 自由記述は Other で受ける。「なんとなく」は、どの秒のどこがそう感じたかまで掘る

## 1.5 投稿予約（任意）

FBで「使える」と判断した本があれば、AskUserQuestionで
「使えると判断した◯本を予約投稿しますか？」（予約する／今回はしない）を聞く。
**ターンを終えずにこのAskUserQuestionへ進める**（会話を終えるとstop_improveフックが
終了を差し戻す。改善フェーズはまだ完了していない）。

- 「予約する」：`.claude/skills/sns-schedule/SKILL.md` の**手順0**から、使える本だけを対象に
  予約投稿を進める（設定確認→開始日・時刻・1日何本のヒアリングからやり直す）。終わったら 2. に進む
- 「今回はしない」：そのまま 2.（材料を集める）に進む

## 2. 材料を集める

`## 詰まった点・QC指摘` に書く。

- 今回のFB
- 制作中の詰まり：エラー、やり直した工程、qc.py の不一致、chop.py のぶつ切り、推測で決めた箇所
- ヒアリングで推奨と違う回答になった項目（推奨の作り方がずれている兆候）
- `references/learnings.md` の過去記録（保留中の意見・却下済みの提案）

## 3. 改善提案を作る

`## 改善提案` に、1提案ずつ次の形で書く。

| 項目 | 内容 |
|---|---|
| ID | I-01, I-02 … |
| 種類 | ヒアリングの推奨値／SKILL.md・rules.md のルール／つまずきどころ／スクリプト／layout.md の実測値 |
| 対象ファイル | 例：`references/rules.md` |
| 削除する内容 | 既存の記述・コード（無ければ「なし」） |
| 追加する内容 | 具体的な文面・コードの要旨 |
| 根拠 | 今回の事実＋過去に同じことが起きた回数 |
| 影響 | 次回から何が変わるか、壊れうるもの |

提案の区分（承認の負担を減らすため）：

- **自動採用可**：テスト付きのスクリプト修正、検査の誤検出を減らす修正、文言の誤りの訂正。
  承認は取るが一括でよい
- **要承認**：絶対ルール・ヒアリング項目・レイアウト・納品物の変更。**1回につき5件まで**。
  超えた分は learnings.md の「保留・観察中」に回し、次回に持ち越す

昇格のルール：

- **1回だけの意見** → learnings.md の「保留・観察中」、または hearing.md の推奨値の調整に留める
- **2回目**、または**事故**（テロップ混入・語尾切れ・個人情報の映り込みなど）→ SKILL.md / rules.md のルール、つまずきどころへ
- **スクリプトの修正** → テストを先に書いてから直す
- **却下済みと同じ提案は出さない**。新しい根拠があるときだけ、その旨を明記して出す
- **理由の無い却下は作らない**。選ばれなかっただけの提案は「保留・観察中（発生回数1）」に残し、
  2回目に同じことが起きたら新しい根拠つきで出し直す
- 既存ルールと矛盾するなら、古いルールの削除も提案に含める。learnings.md の重複統合も提案してよい
- 提案が無い回は「提案なし：理由」と書き、それでよいかユーザーに確認する

## 4. 承認を取る

提案を表で見せ、AskUserQuestion（multiSelect）で採否を聞く。削除を伴う提案は、削除する文面をそのまま見せる。
結果を `## ユーザー判断` に書く（ID ごとに 採用／却下＋理由）。
**却下は `却下：I-01（理由：…）` の形式で理由を必ず書く。**理由が無いものは「保留」に書く
（フックが形式を検査し、理由の無い却下があると `状態: 完了` にできない）。

## 5. 反映する

- 採用した提案だけ反映する。反映後、SKILL.md と references を読み直し、ルール同士が矛盾していないか確かめる
- スクリプトを変えたら `python3 -m unittest discover -s tests`（共通は `.claude/skills/kirinuki_hooks/tests`）と
  `python3 .claude/skills/tests/regression/run.py --ocrcli <ビルドした ocrcli>` を実行し、結果を `## テスト結果` に書く
  （フックが空でないことを検査する。回帰用の実素材 `fixture/clip.mp4` は再配布禁止のためこのリポジトリには含めていない。
  手元に無ければ実行できない旨と代わりに何を確認したかを書く）
- 反映内容を `## 反映結果` に書く

## 6. 記録して終える

- `references/learnings.md` の先頭に今回のエントリを追記する（定量欄・採用・却下・保留をすべて）。
  本文に残すのは直近3回。それより古い回は `references/learnings-archive.md` の先頭へ移す
- **もう片方のスキルにも当てはまる学びかを必ず確認する。** 当てはまるなら
  `.claude/skills/SHARED_LEARNINGS.md` に書き、相手スキルへの展開は次回の提案として保留に残す
- `$D/improve.md` を `状態: 完了` にする
