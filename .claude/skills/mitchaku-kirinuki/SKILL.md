# 密着動画 → ショート切り抜き制作

密着動画のURL（または動画ファイル）から、ショート切り抜きを指定本数（既定5本）制作する。
回答・成果物は全て日本語。実制作は ffmpeg＋scripts/ のツールで行い、**シーン選定と文言はClaudeが判断する**。

## 絶対ルール（この4つは必ず守る）

1. **カットの繋ぎによるテロップの表示ずれをなくす**
   カット頭＝新テロップの最初のフレームにスナップ。カット尻＝次のテロップに変わり始める
   1フレーム以上手前。前後カットのテロップが1フレームでも混入したら作り直し。
   出現後0.5秒未満で切られるテロップ（フリッカー）も禁止＝表示しきってから切る。
2. **冒頭のフックを意識したシーン選定**
   C1（フック）は「いちばん強い一言・画」から入る（異常性ワード・数字・ギャップ発言）。
   結果画面の音読や文脈前提の出だし（「2つ目が」等）は引きが弱いので使わない。
3. **ハイライト→本編のトランジションは、話が飛ぶときだけ使う**
   フック→本編で話や場面が明らかに飛ぶときだけ、白フラッシュ0.35秒（xfade=fadewhite＋acrossfade）で繋ぐ。
   同じ場面・同じ話の流れが続くときは素のカットにする（clips_plan の `flash_after` を `None`）。
   本編のカット同士も素のカットでよい（2026-10-13 凪さん密着のFB）。
4. **文脈がつながらないシーン繋ぎ・終わり方はしない**
   - 繋ぎ：前のカットの語尾と次のカットの頭が会話として読めること。質問→答えの順を守る
   - **1動画1メッセージ**：見出しのコピーに沿わない場面は入れない。本編はフック以外を
     元データの時系列順に1〜2区間でつなぎ、話題の違う区間を3つ以上継ぎはぎしない
   - 終わり：**段落の言い切り**で終える。テロップの区切り＝文の区切りではない。
     「〜するぞ」等の引用止め・「〜と思うんですよ(ね)」等の段落途中・「〜ので」「〜し」の
     継続形で終えない。質問テロップが答えのないまま画面に残る終わり方も禁止
   - 判定は「OCR本文の語尾が言い切り(す/た/ね/か/？)か」＋「終点前後に-30dBの無音の谷があるか」
     の2軸で機械的に出し、必ず文字起こしで前後の発話まで読んで人が確認する

## 毎回の進め方（フックで強制される）

```
0. ヒアリング（グリルミー） ─┐ 並行
1. 素材取得と下ごしらえ ─────┘
2〜7. 制作（ヒアリング確定まで、ベース画像生成と書き出しはフックが止める）
7.5. 完成動画アーティファクト公開
8. FB → 改善フェーズ（終わるまで、終了はフックが差し戻す）
```

- 作業フォルダ `$D`（スクラッチパッド配下 `mitchaku/<動画ID>`）を最初に決め、全工程をそこで行う
- Bashは呼び出しごとにシェルが変わる。**同じコマンド内で `D=/絶対パス` を定義し `cd "$D" && ...` で実行する**
  （フックがコマンドから作業フォルダを読むため。書き出しは `$D/out/` に置く）

### 0. ヒアリング（必須）

`references/hearing.md` の手順で、1問ずつ深掘りして前提を固める。素材取得とテロップ走査は待たずに裏で走らせる。

- 先に `references/learnings.md` を読み、過去のFBから推奨回答を作る
- `templates/hearing.md` を `$D/hearing.md` にコピーし、決まった項目から埋める
- telops.txt ができたら候補シーンを提示して選んでもらう（これもヒアリングの一部）
- 全項目が埋まったら要約を見せて確認を取り、`状態: 確定` にする
- **`状態: 確定` でない間、`render.py`／`mkbase.py` の実行は gate_hearing フックが拒否する**
  （記録の先頭の `skill:` 行が持ち主。素材取得・テロップ走査・QCは止めない）

## フロー

### 1. 素材取得と下ごしらえ
```bash
S="$CLAUDE_PROJECT_DIR/.claude/skills/mitchaku-kirinuki/scripts"

yt-dlp --cookies-from-browser chrome -f "bestvideo[height<=1080][ext=mp4]+bestaudio[ext=m4a]/best" -o src.mp4 <URL>
yt-dlp --cookies-from-browser chrome --skip-download --write-auto-subs --sub-langs ja -o cap <URL>   # 文脈確認用
swiftc -O -o ocrcli "$S/ocr.swift"
python3 "$S/subscan.py" src.mp4     # → telops.txt（全テロップの開始/終了時刻＋本文）
ffmpeg -i src.mp4 -af "silencedetect=noise=-30dB:d=0.08" -f null - 2>&1 | grep silence > silence30.txt
```
- telops.txt が**唯一のカット座標系**。カット点は必ずこの表のフレームに合わせる
- VTT字幕はタイミングが不正確なので文脈把握のみに使い、カット点には使わない
- **Bashでは `$CLAUDE_PROJECT_DIR` が空のことがある**。空なら `S=` をリポジトリの絶対パスで定義する
- **素材がFrame.ioの共有リンク（f.io／next.frame.io）のとき**：yt-dlpは非対応。ブラウザで共有ページを開いて再生し、
  `performance.getEntriesByType('resource')` から `sahls.frame.io/encode-hls/<asset>/token/<JWT>/` を拾う。
  `<base>/h264_1080_best/media-vid.m3u8` と `<base>/aac_cha2/media-aud.m3u8` を
  `ffmpeg -i <映像> -i <音声> -map 0:v -map 1:a -c copy src.mp4` で結合する（トークンは数時間で失効）。
  自動字幕が無いので、文脈把握用の文字起こしは `whisper-cli`（例：ggml-large-v3-turbo、`-l ja -osrt`）で作る
  （2026-08-31 AI活用ラボ13、2026-10-12 凪さん密着V5 の2回）

### 2. シーン選定（Claudeの仕事）
- 本数分のテーマを**目的に合わせて配分**する。密着の目的が認知・信頼性担保なら
  顧客向けメッセージ・人柄ギャップ・実績・ビジョンに分散。採用目的なら働く環境・人間関係寄り
- 各本の構成：C1フック（6〜13秒）→（話が飛ぶときだけ白フラッシュ）→C2以降の本編（合計52〜58秒目安。
  参考の公開密着ショートは45秒前後もあり、45〜59秒なら可。1メッセージに絞った結果短くなるのは可）
- **1本＝1メッセージ**。先に見出しのコピーを決め、それを言い切る場面だけを選ぶ（名場面を集めて並べない）
- 密着ジャンル実測（n=293）で有意なのは「異常性ワード」のみ。フックと見出しに必ず1つ入れる

### 3. カット点の決定
```bash
python3 "$S/cutpoints.py" telops.txt   # telops×無音×(任意)Whisperの候補表。「要注意」列を見る
```
- まず `cutpoints.py` で候補表を機械的に出す（語尾分類・終点前後の無音・次の発話までの間）。
  「要注意」の行は語尾が言い切りでない、または終点に無音の谷が無いことを示す（下記絶対ルール4参照）
- 頭：telops.txt の対象テロップ開始時刻の直後0.01〜0.08秒（無音内が理想）
- 尻：①言い切りの語尾 ②-30dBの無音の谷 ③次テロップ切替の1フレーム以上手前、の3条件を満たす点
- **音声はテロップより先に始まり後まで続くことがある**。頭出しでフックの初語が欠けないか、
  尻で語尾が欠けないか、silence30.txt で発話の実際の終了を確認する
- **テロップ本文＝発話とは限らない**（テロップが言葉を補うことがある）。カット点の候補が決まったら、
  **必ず `scripts/align_check.py` を通す**（発話の頭・尻とテロップの一致をWhisperの単語時刻で検査する。
  NGが出たら直してから先に進む。自動字幕＝cap.ja.vttはタイミングが不正確なので文脈把握のみに使い、
  一致確認には使わない）
- 話が飛ぶ箇所は無テロップ区間（作業画面等）をブリッジに挟むか、質問テロップから入れて繋ぐ

### 4. レイアウト（密着シリーズ実測値・1080x1920）
ある企業チャンネルの公開済み密着ショート3本の実測で全本一致した値。
**自チャンネルの公開ショートで実測し直してから使う**（以下はその実測例）：
- 黒背景。見出し2行センター：1行目 中心y=328・88px級／2行目 中心y=449・109px級
- 文字はヒラギノ角ゴW9、白＋黄(250,250,30)で強調語だけ黄色。**最大幅880px**（超えたら自動縮小。
  モバイル見切れ防止。実測の左右マージンは88px以上）
- 映像はフル幅 1080x606 @y=552（元テロップ焼き込みをそのまま使う。自前テロップは作らない）
- 下部に赤引用 (223,0,13)・80px級・中心y=1264・最大幅860px・全編静止表示。
  本編中で実際に回収される発言のほか、**動画の要点を言い切る引きの強いコピー**（例：「COOの意外な努力」）でもよい。
  どちらにするかはヒアリングで聞く。本編の一言を使う場合も、意味が伝わらない短い相づち（例：「そこで考えた」）は使わない。
  **ネガティブに読める文言は使わない**（引きは「続きが気になる前向きな一言」で作る）。CTA帯（本編はこちらから）はこの形式では使わない
- ベース画像は `render.py` が `clips_plan.py` の l1／l2／quote（[(文字列,'w'|'y'|'r'),...]）から
  `$D/base/base_NN.png` に自動生成する（手でmkbaseを呼ぶ必要はない）

### 5. レンダリング（scripts/render.py）

```bash
D=/絶対パス/作業フォルダ
S="$CLAUDE_PROJECT_DIR/.claude/skills/mitchaku-kirinuki/scripts"
python3 "$S/render.py" "$D" "$D/clips_plan.py" --out out       # --only <ファイル名> で1本だけ
```

- カット点はフレーム格子にスナップされ、`$D/out/<出力名>.timeline.json` に
  カットごとの開始フレーム・フレーム数が書き出される。**QCはこの表を座標系に使う**
- trim＋concat**フィルタ**で1コマンド書き出し（個別mp4のconcatデムクサはA/Vズレが累積するので禁止）
- xfadeは両入力に settb=1001/30000 を挟む（timebase不一致でエラーになる）
- 各カット頭尻に0.10秒afade、ラスト0.35秒フェードアウト
- trimの境界は半フレーム前倒し・`-t`は半フレーム延長する安全マージンを持たせている（`-ss`の丸め誤差でカット端の1フレームが落ちるのを防ぐ）
- ラウドネスの判定・検証はebur128のIntegrated loudnessに統一（loudnormのprint_format=json
  は実測より低く出る系統的バイアスがあるため使わない）。目標-14 LUFSから0.2LU超で補正を開始し、
  最大2回まで（1回目loudnorm・2回目volume、True Peak上限を超えないようクランプ）。最終的に
  許容範囲（I±0.5、True Peak上限あり）に収まらなければ、render.pyがexit code 2で未解決を知らせる。
  映像と音声の長さもここで必ずそろえる

### 6. QC（全本必須）
```bash
python3 "$S/scan_qc.py" out/*.mp4   # 5fps全編OCR→0.5秒未満表示のテロップ検出
python3 "$S/qc_cuts.py" clips_plan.py  # 各カット頭尻をOCRし telops.txt と照合（NGがあれば終了コード1）
python3 "$S/align_check.py" clips_plan.py  # 手順3で確認済みだが、実際のカット点で最終確認する
```
- カット定義は `$D/clips_plan.py` に書く（`CLIPS=[{file, l1, l2, quote, cuts:[(start,end),...]}]`）。
  ベース画像生成・書き出し・qc_cuts.py が同じ定義を読む
- qc_cuts.py は timeline.json のフレーム番号で頭尻を抜き、期待テロップと照合する
  （各カットの先頭フレーム・2フレーム目・最終フレーム・最終から2フレーム目。1フレームでも混入したらNG）
- ffprobeで 1080x1920・元fps・尺・映像と音声の長さの一致、ebur128で -14±0.5 LUFS・True Peak上限
  以内を確認（render.pyの終了コードが2ならラウドネス未解決なので中身も見る）
- ベース画像の文字幅が880px以内に収まっているか実測

### 7. 納品
デスクトップに `<企画名>_切り抜き◯本_YYYYMMDD/` を作り、
mp4（連番_内容.mp4）＋ 00_はじめに.txt（仕様・変更履歴・未実施）＋ 投稿タイトル案.txt
（下の文法・各本2〜3案＋根拠）＋ 編集指示/（各本のカット表＝元データのタイムコードと
テロップ全文、修正履歴）を入れる。SendUserFileでmp4を送る。
**投稿時タイトルも必ず併記する**：各本の本命1案を「投稿時タイトル」として決め、
納品時のチャット報告の一覧表に動画名と並べて記載する（ファイルを開かなくても
そのまま投稿できる状態で渡す）。

#### 投稿タイトルの文法（自チャンネルの実測から作る）
`yt-dlp --flat-playlist --print "%(view_count)s|%(title)s" <チャンネル>/shorts` で
再生数つきの一覧を取り、上位の密着系ショートの共通型を洗い出してから書く。
以下はある企業チャンネルの密着系4本（最高再生は最下位の約12倍）で観測された型。
自チャンネルの実測がこれと違ったら、実測のほうを優先する：

- **2ブロック構成**。「。」または「…」で割る。前半＝ギャップの起点か発言引用（鉤括弧）、
  後半＝数字＋属性＋体言止め
- **数字と属性を必ず入れる**（金額・年数・件数などの数字／役職・年齢・経歴などの属性）
- **体言止めで締める**：「〜の理由」「〜のリアル」「〜との葛藤」「〜に密着」「〜の1日」
- **バナー見出し・赤引用はタイトルに再利用してよい**。最高再生の1本は赤引用をそのまま
  タイトル頭に置き、バナーで使った数字も重複させていた。重複回避より型の踏襲を優先する
- **使わない**：矢印「→」／語尾の「w」／「〜しました」等の口語文。
  ただしこれは「そのチャンネルに前例が無い」という理由なので、自チャンネルの実測で確認する

### 7.5 完成動画アーティファクト

納品物ができたら、動画を見られるページ（アーティファクト）を作って共有する。

```bash
D=/絶対パス/作業フォルダ
python3 "$CLAUDE_PROJECT_DIR/.claude/skills/sns-schedule/scripts/schedule.py" preview \
  "<納品フォルダの絶対パス>" --out "$D/preview"
```

- **20MiB上限に対し19MiBで判定（余裕1MiB）**。19MiB以下のクリップはそのまま、超えるものは
  幅720px（高さは自動でアスペクト比を維持）・crf28（それでも超えたらcrf32）で再エンコードして
  `$D/preview/` に並べる。**`$D/out/` には書かない**（Stopフックの再発火防止）
- 各本のデータ（投稿時タイトル・「投稿タイトルの文法」節の代替案と根拠・尺・サイズ）に加え、
  トップレベルの `main_video_url` に `$D/hearing.md` の `## 本編URL` 節の値を入れたJSONを作る。
  `gallery` コマンドでHTMLを生成する:

  ```bash
  python3 "$CLAUDE_PROJECT_DIR/.claude/skills/sns-schedule/scripts/schedule.py" gallery \
    --data "$D/gallery_data.json" --out "$D/preview/page.html"
  ```

- Artifact toolでこのHTMLを公開する（`capabilities: {"assets": {}}`、アイコンは`video`）。
  公開後、`upload_asset`アクションで `$D/preview/` の各mp4を添付する（1回の呼び出しにつき最大25本）。
  返ってきたURLを各クリップの `video_url` に設定してデータJSONを作り直し、`gallery` で再生成して
  **同じファイル**へ再公開する
- 公開したURLを `{"url": "..."}` の形で `$D/artifact.json` に保存する（後で予約案を追記する際に使う）
- ユーザーにリンクを渡す。**このページは組織内限定（organization-internal）**であることを伝える

### 8. FB と改善フェーズ（毎回必須）

納品したら終わりにしない。`DREAM.md` の手順で実施する。

- 各本のFB（使えるか・良かった点／悪かった点とその理由）をユーザーに聞く
- FBが終わったら、改善提案に入る前に `DREAM.md` の **1.5 投稿予約（任意）** に進む
  （使える本があれば予約投稿するかどうかを確認する）
- 今回のFB・詰まった点・QC指摘と `references/learnings.md` の過去記録から改善提案を作る
- 提案ごとに対象ファイル・削除する内容・追加する内容・根拠を見せ、**承認を得たものだけ**反映する
- `templates/improve.md` を `$D/improve.md` にコピーして記録し、`状態: 完了` にする。learnings.md にも追記する

  （注意は mp4 の顔ぶれが前回から変わったときだけ。1回の終了につき1回で、続けて終えれば通る）

## 過去に踏んだ罠（同じ失敗をしない）
- 決意表明の引用（「〜するぞ」）で終わるテロップ末で切ったら、発話は「〜というのをお伝えして
  始めていますし」と継続していて文中切りになった。**引用止めのテロップは要注意**
- 「〜と思うんですよ」で切ったら段落はその2文先まで続いていた。**言い切りでも段落の途中がある**。
  終点は文字起こしで段落の終わりを確認する
- フック頭をテロップ途中に置いたら、音声が単語の途中から始まって意味が取れなくなった。
  頭は質問テロップの初フレームか、発話の開始前の無音に置く
- 「すごいですね」が出て0.2秒でフラッシュに切られた。リアクションテロップも表示しきる
- yt-dlpの403は --cookies-from-browser chrome で回避
- **フェードインするテロップ（質問テロップに多い）はsubscanが取り逃す**（telops.txtでは空白行になる）。
  取り逃した質問テロップが終端に残り、答えの無いまま終わる切り抜きになった事例がある。
  カット頭尻を確定する前に、
  頭尻±数秒の実フレームをocrcliで直接OCRして空白行の実体を確認する
- scan_qcの警告は元動画焼き込みバナーのOCR揺れで誤検出することがある。該当時刻の実フレームOCRで裁定する
- フックをテロップ「結果が出てるのに評価されてない人とかも」の頭で切ったら、発話は
  「…結果が出るみたいな人って絶対いるんですよ。出てるのに評価されてない人とかも」で、
  **「結果が」はテロップが補った語だった**。音声が「出てるのに」から始まり、字幕と食い違った（2026-09-15）
